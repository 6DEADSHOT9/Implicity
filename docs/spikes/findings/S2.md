# S2: PostHog query delay

**Result:** PostHog events were queryable in a measured 5.4–6.6 seconds in these trials. Recommend a **10 second evaluation delay** after a Session ends, with the existing catch-up evaluation at the next Session start covering anything missed.

## Measurements

| Events in batch | Repeats | Median until fully queryable | Worst |
|---:|---:|---:|---:|
| 1 | 5 | 6.43 s | 6.58 s |
| 100 | 5 | 6.51 s | 6.54 s |
| 1,000 | 5 | 6.49 s | 6.61 s |

Each batch used a unique marker and client timestamp. A query was polled about once per second; a changing literal prevented reuse of a cached query result. The complete raw timings are in [`s2-timings.csv`](../../../spikes/s2-s3-posthog/s2-timings.csv).

A placeholder `session_summary` Event with 30 numeric properties was also queried; all values matched. Result: [`s2-session-summary.json`](../../../spikes/s2-s3-posthog/s2-session-summary.json).
